Added [Constraint][esmporium.requirements.Constraint], which judges what is *in* the
datasets a requirement selected rather than which dataset it is: whether the control a
run branched from covers the years being analysed, whether two variables span the same
period. A constraint is anything with an `evaluate(view, catalogue)` method returning
[Pass][esmporium.requirements.Pass], [Degraded][esmporium.requirements.Degraded] or
[Fail][esmporium.requirements.Fail], and must be a pydantic model if its requirement is
to be stored. Attach it with
[Leaf.with_constraints][esmporium.requirements.Leaf.with_constraints], on a leaf or on a
node above it, or to the [Requirement][esmporium.requirements.Requirement], which sees
every role in the group at once and so is where a check comparing one dataset against
another goes.

- [Covers][esmporium.requirements.Covers] is the first constraint we ship: one dataset
  in a lineage has to cover the span of another. Nothing records a dataset's time range
  yet, so it needs a catalogue providing
  [CatalogueWithTimeInfo][esmporium.requirements.CatalogueWithTimeInfo], which neither
  of ours does.
- `Constraint` is generic in the catalogue it needs, so a constraint needing more than
  [Catalogue][esmporium.requirements.Catalogue] provides declares a protocol beside
  itself. A constraint which raises is reported as failing, with the error in the
  explanation.
- A group which met every constraint but not as well as it could is
  [ExplanationStatusOk.DEGRADED][esmporium.requirements.ExplanationStatusOk], with the
  reason on [Solution.notes][esmporium.requirements.Solution.notes]: the analysis can be
  run, with something to say in the write-up.
