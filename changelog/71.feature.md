Added the time information ESGF's search APIs may not publish, as values and as pure
measurement, ahead of anything storing it. [esmporium.datasets.time][] holds a step,
units, a time axis, a half-open time range, a span and a
[BranchPoint][esmporium.datasets.BranchPoint]; [esmporium.enrich][] reads a version's
range out of its filenames ([measure_version][esmporium.enrich.measure_version]) and a
calendar and units out of a file's time-variable attributes
([read_time_axis][esmporium.enrich.read_time_axis]). None of it is wired to a search, a
database or a solve yet.

- Calendar arithmetic is [esmporium.datasets.calendars][], a thin wrapper over `cftime`,
  which is the new optional `calendars` extra. A monthly or yearly axis never reaches
  that import, because twelve months is a year in all six CF calendars, so only daily
  and sub-daily data needs `esmporium[calendars]` installed.
- What is project-specific is a registry you can add to or override:
  [FILENAME_TIME_READERS_BY_PROJECT][esmporium.enrich.FILENAME_TIME_READERS_BY_PROJECT]
  for how a project writes its filename range (the four projects esmporium has a query
  class for -- CMIP5, CMIP6, CMIP6Plus and CMIP7 -- and no others, because an entry is
  a claim about a convention we have seen rather than a guess that one project writes
  filenames like another),
  [SPAN_BY_REPORTING_INTERVAL][esmporium.enrich.SPAN_BY_REPORTING_INTERVAL] for how wide
  one step of a frequency is, and
  [NO_TIME_AXIS_INTERVALS_BY_PROJECT][esmporium.datasets.NO_TIME_AXIS_INTERVALS_BY_PROJECT]
  for the frequencies with no time axis at all, which have no range rather than an empty
  one.
- A measured range records whether the version's files actually fill it and how many
  were measured, so a gap, an overlap or a file published since is visible rather than
  smoothed over.
